# ROS-10：用证据判断系统在做什么

[学习指南](../学习指南.md) · [知识索引](../知识索引.md#ros-10) · [提示与答案](../参考答案/ROS-10_参考答案.md)

## 导读

**为什么学这一节。** 系统显示运行中或停止中，不代表每一层正在做相同的事。明确状态与证据，可以让联调和失败处理更有依据。

**学完会有什么变化。** 从看到failed就重启整个系统，进到按最后正常边界追查，并能区分停止发命令、取消任务和实际运动停止。

**接下来能做什么。** 可以给学习系统设计可解释的状态记录与超时处理，衔接[CTRL-09](../../04_机器人控制与运动规划/讲义/CTRL-09_约束超时与停止.md#intro)和[SIM-06](../../06_仿真与系统集成/讲义/SIM-06_模型与接口适配.md#intro)中的执行检查。

## 学习目标与资料

日志与最短排错顺序从 W02 开始用；控制状态和停止交互放到 W11 的模拟环境。先建立解释与验证能力。

## 按失败发生的位置排查

```text
环境/启动 → 节点与参数 → 名称/类型/QoS → 数据字段与时间
    → 模型/TF → 控制器/接口 → 驱动写入 → 状态与任务结果
```

不要每次从第一项重查全部。根据最后一个已确认正常的边界，继续往后缩小。

| 观察 | 优先寻找的证据 |
|---|---|
| 看不到节点/包 | 实际环境、包前缀、启动错误、进程是否退出 |
| 有话题但没数据 | 发布者、类型/QoS、发现环境、spin/回调 |
| 数据来了但模型不对 | 名称映射、单位、URDF、frame/时间 |
| 命令发了但反馈不变 | 目标接口、active/claim、控制器输入、write/read、设备状态 |
| 软件报告成功但任务失败 | 成功定义、实际反馈、标定与物理任务证据 |

日志至少留组件、事件阶段、关联目标/样本、时间来源、关键数值与失败原因。保存完整异常，不只截最后一句“failed”。

## 状态与停止要分层解释

应用层可以维护 INIT、READY、RUNNING、STOPPING、STOPPED、FAULT 等清楚状态；每个状态允许什么输入、靠什么证据转换，要自己定义。

停止生成新命令、取消当前 action、控制器进入对应保持/停止行为、硬件真正停止，分别发生在不同层。下层可能仍执行已接收轨迹或缓存命令。

“发零”也要知道接口含义：零位置、零速度、零力矩不是同一件事。真实平台按其规定执行停止/急停，学习阶段只在合成输入和模拟硬件中验证软件行为。

## 输入可用性的几项基础检查

- 状态与控制器满足当前任务要求；
- 数据最近收到且采样时间有效，时钟关系清楚；
- 名称、单位、坐标、维度一致；
- 数值有限、位置范围符合当前模型/任务；
- 目标、反馈和超时有对应关系，不能无限沿用旧观测。

这些是基础软件检查，不构成完整的运动可行性或硬件安全论证。轨迹速度/加速度、接触与设备故障还要对应实验。

## 练习

<a id="ex1"></a>

### 第 1 题：给三个问题各写最短排错链。约 20 分钟

A：topic list 有 joint_states，但记录器没收到。

B：记录器收到数据，RViz 模型姿态不对。

C：应用打印命令已发送，但关节状态不变。

每种情况只写前三项高价值检查，以及什么证据能让你转到下一项。

<a id="ex2"></a>

### 第 2 题：arm_controller 这几个字到底指什么？约 15 分钟

假设你看到：

```python
class ArmController(Node):
    def __init__(self):
        super().__init__("teleop_bridge")
        self.pub = self.create_publisher(
            JointTrajectory, "arm_controller/joint_trajectory", 10,
        )
```

另有控制器 YAML 声明名为 arm_controller 的 JointTrajectoryController。分别解释类名、节点名、话题路径和控制器实例名。你还要看什么才能证明消息确实到达该控制器？

<a id="ex3"></a>

### 第 3 题：写一个离线命令输入检查。约 25 分钟

实现两关节的位置输入检查：控制器 active、最近接收状态未超时、输入长度正确、数值有限且在给定范围内时返回 (True,"ready")；否则返回明确拒绝原因。

检查范围用 [-1,1] rad；接收新鲜度按同一 steady clock 的整数 ns。配置自身无效要报错。本题选择拒绝越界输入，不静默把它裁成另一条命令。

测试未收到、超时、NaN、越界、inactive 与正常输入。函数不连接实际控制器。

<a id="ex4"></a>

### 第 4 题：停止请求走到了哪里？W11 后续约 25 分钟

一个策略节点收到 stop 后停止推理并不再 publish，但模拟轨迹控制器仍持有之前的目标。

画出要核对的各层，设计一次模拟观察：应用停止状态、当前 action/控制器状态、期望与实际关节状态、完成/取消/超时结果分别怎样记录？

给出“仅停止上游”和“执行端按协议处理停止”的证据差别，最终行为以选定演示控制器版本为准。

## 直觉与回顾

排错像沿交接点查一份任务：上一位真的交出了什么，下一位真的收到了什么。只看最上层一句日志，常常只能知道它完成了自己的那一步。

能坦然写“目前只确认到这一层”，会让问题更容易被解决。复盘画一个停止请求的路径，并标出你已经有证据的位置和下一项要观察的位置。
