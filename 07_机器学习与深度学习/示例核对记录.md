## 主项目：CUDA FP32 的 FK 函数近似

固定数据：train/val/IID/OOD seed=7/8/9/10，数量 512/128/256/256。范围、连杆与单位见[学习指南](学习指南.md)。数据在 CPU 生成，再搬 batch 到 GPU；CPU/GPU 共用相同样本、CPU 初始化权重与划分，避免把“相同整数 seed”误当成不同后端独立生成数据必然一样。

train 输入均值约 [-0.016979,0.021778] rad，尺度 [0.586139,0.694188] rad；标签保持米。Linear2→2 为 6 参数；Tanh MLP2→32→32→2 为 1218 参数。

## CUDA FP32 / AMP：在新进程接着训练

数据为 64 个 FK 样本 seed25，直接用原始 rad 输入；模型 Linear2→16、Tanh、Dropout0.25、Linear16→2。模型 seed21、loader seed22，Adam lr0.01、batch16，6 epoch（24 次训练调用）。

对每种精度分别比较连续 6 epoch，与 3 epoch 后保存、启动另一个 Python 进程加载并继续 3 epoch。FP32 用 run_epoch；AMP 用 cuda_amp_step，clip max_norm=1，scaler init_scale=128、growth_interval=4。两种精度各自核对恢复，不比较它们必须同一轨迹。

完整保存/恢复模型、Adam、next_epoch、CPU RNG、CUDA RNG、loader generator 和 AMP scaler。新进程重建对象后最后恢复 RNG；模型在 GPU，再创建 optimizer，然后加载状态。读文件使用 map_location=cpu、weights_only=True。

两种精度均通过：后半 loss 逐值一致，最终参数最大差 0；optimizer、CPU/CUDA/loader RNG 与 scaler 状态也分别一致。证明了本次同设备/版本、单进程、epoch 边界的接续。CPU 入门恢复实验也重跑通过，但那部分是同进程重建。

| 新进程恢复时遗漏项 | FP32 最终权重最大差 | AMP 最终权重最大差 |
|---|---:|---:|
| 无遗漏 | 0 | 0 |
| Adam 状态 | 0.105401 | 0.100771 |
| loader RNG | 0.027896 | 0.027849 |
| CUDA RNG | 0.028652 | 0.029128 |
| scaler 状态 | 不适用 | 0，但 scaler 不一致 |

AMP 完整恢复最终 scale=8192；遗漏 scaler 时最终 scale=1024。本例遗漏 scaler 没有改变最终权重，却没有恢复完整训练状态。因此只比权重或一轮 loss 不足以验证完整接续；也不能说“漏任何状态一定会让权重变化”。

没有验证 batch 中途、多 worker、多 GPU、随机增强、scheduler 或跨版本恢复。继续选择 best 还要保存历史 best_val/最佳权重与日志，状态片段不会替你组织这些项目文件。

## 资源短测：CUDA FP32 较快，AMP 在本例反而较慢

同一 TinyCNN 与 CPU 初始化权重，输入固定为 64×1×16×16 合成图，Adam lr0.003、梯度裁剪1。每个模式启动独立进程，预热10步，再测3组×40步；三组连续训练，不在每组之间重置参数。GPU 在窗口前后 synchronize；CPU 为单线程。

数据预先驻留目标设备，不含读盘、生成图像、DataLoader、CPU→GPU 传输、模型初始化与预热。计时含前向/损失/反向/裁剪/更新，AMP 还含 scaler；有限值检查和 item 在窗口外，避免每步同步。该测量循环与答案中每步检查/返回 item 的教学 helper 有不同计时边界。

| 模式 | 三组 ms/step | 中位 ms/step | 约样本/秒 | 峰值 allocated / reserved MiB |
|---|---|---:|---:|---|
| CPU FP32，1线程 | 2.216 / 2.218 / 2.187 | 2.216 | 28886 | 未测 CPU 内存，不适用 CUDA 计数 |
| CUDA FP32 | 0.873 / 0.844 / 0.906 | 0.873 | 73304 | 69.873 / 88.000 |
| CUDA FP16 AMP | 1.229 / 1.188 / 1.120 | 1.188 | 53858 | 65.811 / 68.000 |

GPU 显存是当前测试进程的 PyTorch 计数：allocated 统计当时活跃的相应分配，reserved 还包含 allocator 保留的缓存；不含所有进程和驱动的全部开销。三个窗口峰值分别一致，原始数组见 JSON。不能用这些峰值直接预测更大图像/序列的上限。

在这个很小的模型上，AMP 的峰值 allocated 略低，耗时却高于 CUDA FP32。这里只观察到当前配置的结果，没有做算子 profiling 来归因。笔记本功耗/温度、桌面负载、CPU 线程数与计时边界都会影响比例；不能把一次短测当成所有任务的性能保证。最终 loss/grad 有限性已检查，资源短测不作为模型质量对比。
