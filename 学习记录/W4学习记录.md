### 读到什么（这里承接W3学习记录中11-22的内容）
3. Understanding services
- 服务（services）基于调用—响应模型，只有在被客户端（client）调用时才响应，可以有多个服务端和客户端
- ros2 service list返回当前活动的服务，其中六个带parameters的服务为通用服务，在命令后加--show-types(-t)返回服务列表，服务后的[]中的内容为服务的类型
- ros2 service type <service_name>返回服务的类型，类型为std_srvs/srv/Empty时，请求和响应都没有数据
- ros2 service info <service_name>返回服务类型、客户端和服务端的数量
- ros2 service find <type_name>返回使用该类型的所有服务
- ros2 interface show <type_name>返回服务的参数结构，用---分割，上半部分为请求结构也就是我们要关注的，下半部分为响应结构
- ros2 service call <service_name> <service_type> (opt:<arguments>)具体调用服务
- ros2 service echo <service_name | service_type> <arguments>查看服务客户端和服务端之间的数据通信，然而服务的内省默认关闭，必须先设定configure_introspection参数为contents才能读取到信息
- 服务不适合持续调用，相比之下话题更适合；但话题是一种单向消息，而服务是双向的
4. Understanding actions
- 动作（action）是面向长时间运行任务的通信方式，由目标（goal）、反馈（feedback）和结果（result）组成
- ros2 action list返回活动中的动作列表，在结尾加--show-types(-t)返回动作列表，包括动作类型
- ros2 action type <action_name>返回动作的类型
- ros2 action info <action_name>返回动作的信息，包括动作的名称、客户端和服务端
- ros2 interface show <action_type>返回动作类型消息的结构，由---分割，最上面是目标goal请求的结构，中间是结果result的结构，最后是反馈feedback的结构
- ros2 action send_goal <action_name> <action_type> <values>发送动作目标，<values>的形式与之前一致为YAML格式，delta为变化量也就是结果；在结尾加上--feedback可以在结束前持续接收到反馈，remaining是动作剩余，反映了进度

### 我的理解
- ROS2把复杂系统拆分成模块化节点，每一个节点都是相对独立的一个功能合集
- 话题、服务、动作都是通信方式，都有自己的消息类型，都是用来联系不同节点的通信方式，三者都有自己适合的方面
- 话题是多对多的（发布者不指定订阅者），服务是请求—响应式的；但内省默认关闭是出于运行时开销（启用后节点要额外发布内部通信数据），与服务是否点对点无关
- 对于话题，订阅端和发布端都存在于节点中；对于服务，服务端和客户端都存在于节点中，对于动作，动作服务端和动作客户端都存在于节点中
- 话题，服务和动作的命令行工具格式基本一致

### 还没懂
- （已解决）内省的含义：“内省（Introspection）”指的是让程序节点自己观察并主动向外汇报自己内部正在发生的通信细节

### 小结
- 节点（node）的核心为：命名空间（Namespace）+节点名（Node Name）+内部通信接口（Publishers/Subscribers/Services/Actions/Parameters），用来“承载”通信功能，一个可执行文件可以包含一个或多个节点
- 话题（topic）的核心为：**发布者（Publisher）**+话题名（Topic Name）+消息类型（Message Type，.msg）+**订阅者（Subscriber/Subscription）**，四者都要对应上才能发送和接收数据，QoS（服务质量策略）也必须兼容才能成功连通
- 服务（service）的核心为：**客户端（Service Client）**+服务名（Service Name）+服务类型（Service Type，.srv）+**服务端（Service Server）**，服务是点对点的，同样要求都匹配才能成功通信
- 动作（action）的核心为：动作客户端（Action Client）+动作名（Action Name）+动作类型（Action Type，.action）+动作服务端（Action Server），动作适合更复杂的任务，一样要对上消息类型
- 内容比较多，但三种通信方式使用方法和结构比较类似，总体来说比较有规律可言，都有比较鲜明的使用方向
