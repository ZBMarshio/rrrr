# ENG-07：保存一段能解释的修改

[学习指南](../学习指南.md) · [知识索引](../知识索引.md#eng-07) · [提示与答案](../参考答案/ENG-07_参考答案.md)

## 导读

**为什么学这一节。** 学习需要不断试改，也需要随时知道哪些修改有效。Git让一次实验的代码变化可以查看、说明和恢复。

**学完会有什么变化。** 从担心改坏后找不回原版，进到能区分工作区、暂存区与提交，查看差异，并在独立分支尝试一个清楚的改动。

**接下来能做什么。** 可以为小项目保存可解释版本，配合[EXP-03](../../00_公共基础与学习方法/讲义/EXP-03_配置种子与复现.md#intro)追踪实验条件，在后续复现与协作中说明自己的贡献。

## 先看清三个位置

```text
工作区：你正在编辑的文件
    git add 选定此刻的内容
暂存区：下一次提交将记录的内容
    git commit
提交：历史中的快照，HEAD 通常指向当前分支的最新提交
```

git add 不是“以后这个文件的所有修改都会自动进提交”。暂存后再改文件，工作区和暂存区就可以不同。

## 每题使用独立练习仓库

以下是你手动练习的初始化模板，每道操作题从新目录开始。命令中的身份只设置在该临时仓库：

```bash
lesson_repo=$(mktemp -d -t eng07.XXXXXX)
cd "$lesson_repo"
git init -b main
git config user.name "Learning Practice"
git config user.email "learner@example.invalid"
printf 'value=1\n' > notes.txt
git add notes.txt
git commit -m "Add baseline note"
```

mktemp 会创建新目录；记下输出的实际目录，避免找不到练习结果。不要在已有工作区重复这份初始化。

## 要留意的细节

- 运行修改命令前先看 `git status`，理解当前分支与已有改动。`git diff` 看工作区相对暂存区的差别，`git diff --staged` 看暂存区相对 HEAD 的差别。
- 一次提交尽量表达一件完整修改，例如“拒绝非递增时间”，同时包括相关说明或验证；不是按“今天所有文件”随意堆进去。
- 分支记录提交位置。切换分支不等于永远自动隔离你的未提交改动；先处理清楚工作区状态。
- 合并冲突时先理解双方意图，再修改文件、运行验证、add 并完成合并；删除冲突标记只是必要步骤之一。
- `restore --staged` 可以取消暂存并保留工作区；`restore -- file` 则可能丢弃该文件未暂存的修改。运行前说清来源和目标。
- `revert` 创建一个撤销指定提交效果的新提交，保留历史；工作区有改动或后续修改冲突时仍需处理。
- .gitignore 主要影响未跟踪文件，不能让已经跟踪的文件自动消失。虚拟环境、构建目录与大运行产物通常不入库；少量样例和必要配置应清楚保存。

## 练习

<a id="ex1"></a>

### 第 1 题：我刚改的 3 为什么没进提交？约 20 分钟

从初始化模板出发：

```bash
printf 'value=2\n' > notes.txt
git add notes.txt
printf 'value=3\n' > notes.txt
git diff
git diff --staged
git status --short
```

先预测三处分别为几：HEAD、暂存区、工作区。若此时直接 commit，提交记录几？提交后工作区还会有修改吗？

<a id="ex2"></a>

### 第 2 题：处理一次真正的同一行冲突。后续约 30 分钟

用新练习仓库，先提交 `config.txt` 的 `angle_unit=rad`。从该提交创建 feature 分支，将同一行改为 deg 并提交；回 main，将同一行改为 RAD 并提交，再合并 feature。

观察冲突。按我们当前程序只支持小写 rad 的约定解决，验证配置含义，再完成合并。写出两个分支为什么改、你最后为什么选这个结果。

<a id="ex3"></a>

### 第 3 题：三种“撤销”分别改变哪里？约 20 分钟

分别在干净练习状态准备场景：

1. 刚修改并 add 了 notes.txt，只想取消暂存，保留修改。
2. 工作区有一项确认不要的、尚未暂存的 notes.txt 修改，恢复到暂存区内容。
3. 干净工作区中，最新的普通提交被证明有问题，希望保留历史并撤销其效果。

为每个场景选命令，运行前写下哪些内容会保留、哪些会改变。第 2 项确实会丢弃那一项工作区修改，只在本练习文件上做。

<a id="ex4"></a>

### 第 4 题：给轨迹分析留两次有意义的提交。约 20 分钟，随项目做

在你自己的代码练习仓库中，记录两次能分别解释的修改，例如先“保存基线读写和曲线”，再“检查坏时间并补说明”。

写简短 README，记录输入来源、单位、命令、结果和未验证事项。用 diff 检查要提交的文件；说明 .venv、build 和大 runs 产物如何处理。

这一题只给验收标准。你已有可用 Git 项目时直接利用，不需要为每个函数建一个新仓库。

## 直觉与回顾

暂存区像你正在整理的一页实验记录：你挑出的是此刻准备讲清的一段变化。提交之后，别人应该能理解“改了什么、为什么、怎么知道有效”。

Git 带来的踏实感来自有依据地尝试：知道现在状态在哪里，也知道怎样回到一个理解过的状态。先把几次小提交讲清楚，比先背很多命令更有帮助。

复盘时选一个过去想笼统说“回退”的场景，重新描述为“从哪个位置恢复到哪个位置”。
