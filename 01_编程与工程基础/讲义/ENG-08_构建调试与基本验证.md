# ENG-08：用一个小反例把问题缩小

## 导读

**为什么学这一节。** 程序失败时，继续改很多地方很容易失去线索。把错误缩成一个仍能触发问题的小例子，才能验证自己的解释。

**学完会有什么变化。** 从依靠猜测和大段打印，进到能沿读取、验证、计算、构建和执行定位边界，用调用栈或反例检查修复。

**接下来能做什么。** 可以独立处理轨迹工具的错误，为[ROS-10](../../02_ROS2与机器人系统/讲义/ROS-10_排错状态与停止条件.md#intro)的系统排查和[ML-05](../../07_机器学习与深度学习/讲义/ML-05_过拟合泄漏与排错.md#intro)的训练排错建立同一套证据习惯。

## 学习目标与资料

程序出问题时，能指出失败发生在读取、验证、计算、构建还是执行，并用一个最小例子验证自己的解释。Python 部分现在就用，CMake 随 W05 做。

| 资料 | 只读这些内容 |

| [pdb](https://docs.python.org/3.12/library/pdb.html) | breakpoint；p、n、s、c、where 的基本使用 |

版本固定的 CMake 页面便于对照基础命令；你自己的项目仍以实际安装版本和目标声明为准。

## 排错的一次完整循环

1. 写出期望与实际差异，保留原始错误信息。
2. 把数据缩到两三行，让错误仍能出现。
3. 明确一个假设，如“把两个关节平均掉了”或“打开了错误路径”。
4. 在相关边界查看值、形状、类型、单位或调用栈，一次改一个原因。
5. 用已知结果或边界输入复查修复，再回到原任务。

想清楚“什么观察会推翻我的猜测”，排错就更容易停留在证据上。

## 一个值得停下来看的错误

```python
def rmse_bad(errors):
    return abs(sum(errors) / len(errors))
```

它返回绝对的平均有符号误差，不是 RMSE。对某些输入看起来接近正确，对正负抵消的输入会很明显。先找反例，不急着上复杂数据。

调试时可在函数入口放 `breakpoint()`，检查输入与中间量。先会用 `p errors` 看变量、`n` 执行下一行、`c` 继续、`where` 看调用关系；不要把 pdb 命令误写进普通 shell。

## 构建与运行是不同阶段

| 阶段 | 常见现象 | 优先查 |
|---|---|---|
| 配置/生成 | CMake 找不到源文件、包或编译器 | 路径、依赖、CMake 配置 |
| 编译 | 缺分号、类型不匹配、缺声明 | 首个相关诊断与源码 |
| 链接 | 声明存在但 undefined reference | 定义、参与构建的源文件和库 |
| 运行 | 异常、输入错误、数值不对 | 调用栈、数据契约、资源与状态 |

CMake 描述构建目标与依赖，再生成构建系统；执行 `cmake --build` 才进行构建。成功生成 build 目录不代表编译、链接或程序逻辑已经通过。

## 练习

<a id="ex1"></a>

### 第 1 题：找一个能击穿错误实现的反例。约 20 分钟

给 rmse_bad 找一个至少两项的输入，让结果明显错误。独立实现 `rmse(errors)`，要求非空、有限数值，输出均方根；空输入或非有限值抛 ValueError。

先手算预期，再运行。解释为什么随便测一条全正且相等的数据，可能发现不了这个 bug。

<a id="ex2"></a>

### 第 2 题：写少量真正有区分度的验证。约 20 分钟

用 unittest 验证第 1 题函数，至少包括：

- 全零，结果为 0；
- 正负抵消的输入，结果仍大于 0；
- 不同大小误差，结果与手算一致；
- 空输入和 NaN 被拒绝。

临时换回 rmse_bad，确认正常数值测试中至少一项会失败，再换回修复版。不需要为每次 print 或每个简单赋值写测试。

<a id="ex3"></a>

### 第 3 题：错误发生在哪一层？约 15 分钟

分别判断：

1. C++ 语句缺分号，编译器指出 expected ';'。
2. main 调用已声明的 squared_error，但构建只包含 main.cpp，没有包含其定义。
3. 程序正常启动后读取不存在的数据文件。
4. `std::vector<double> q(2); q.at(5);` 在运行时抛 out_of_range。

为每种情况写下一步检查，不要只写“重新编译”。

<a id="ex4"></a>

### 第 4 题：三个源码文件与一个构建目标。W05 选做，约 30—45 分钟

在自己的练习项目中建立：

- stats.hpp：声明 `double squared_error(double observed, double reference)`；
- stats.cpp：实现；
- main.cpp：调用 `squared_error(0.3, 0.1)` 并输出；
- CMakeLists.txt：声明目标，纳入两个 cpp，要求 C++17。

用 `cmake -S . -B build`、`cmake --build build`、`./build/trajectory_demo` 配置、构建和运行。

之后只在练习中暂时漏掉 stats.cpp，观察报错层次，再修复。ROS 2 的 colcon/ament 在这一基础上增加包级构建与发现规则，与 W05 节点任务衔接，不在此题重做整套工作空间。

## 直觉与回顾

调试像逐步缩小搜索范围。一次把十处都改掉，即使恢复正常，你仍可能不知道原因；一个能反复触发的小反例，能让解释变得可检验。

基本测试的价值，是把已经确认过的知识留下来。你今天知道“正负误差不能抵消”，就留一个对应样例，让以后的修改有机会暴露退步。

请写一次自己的“原假设—观察—新判断”，而不只写“改了以后好了”。这会慢慢形成你处理陌生项目的办法。
