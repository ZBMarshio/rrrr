## 沿着一次运行看数据

`config 路径 → 解析配置 → 解析输入路径 → 读 CSV → 转换/验证 → 计算 → 保存图和摘要`。

每一步各自回答一个问题：文件存在吗？字段是什么？字符串如何变成数？单位一致吗？计算结果有限吗？输出到底保存在哪里？

```json
{
  "input": "data/trajectory.csv",
  "output_dir": "runs/baseline",
  "angle_unit": "rad"
}
```

本章约定：**配置中的相对路径，相对 config.json 所在目录解析**。这样从别的目录用配置的绝对路径启动时，数据位置也明确。命令行传入的相对 config 路径仍先按启动时的当前目录解释。

## 容易漏掉的细节

- 读取 CSV 得到的通常是字符串。`"0.1" + "0.2"` 不是浮点加法；在输入边界显式转换。
- CSV 表头和单位是接口的一部分。缺列或顺序变化时用字段名读，不默认第几列永远是同一关节。
- 用 `with ... open(encoding="utf-8", newline="")` 处理 CSV。遇到带 BOM 的文件可明确使用 `utf-8-sig`；不要用忽略错误的解码把坏数据吞掉。
- `float("nan")` 可以成功，转换成功不等于数值有效，仍需有限性检查。
- 日志记录阶段、输入、样本数、形状、单位和失败原因；图里标时间/角度单位。不要在高频循环里打印所有数据。
- 日志时间表示程序记录事件的时间，不自动等于数据采样时间。轨迹图要用文件里的 t_s。
- 日志不替代异常处理。发生输入错误后明确失败；不要输出一份“全零成功结果”。
- 输出目录沿用同名文件时可能覆盖旧结果。学习阶段可用清楚的运行名；同一运行说明覆盖规则。
- JSON 摘要要能被普通 JSON 工具读取。非有限数先处理；Python 写入时可用 `allow_nan=False` 拒绝 NaN/Infinity。

## 直觉与回顾

文件路径可以想成一张地址：相对路径需要一个出发点。你在代码里写了同样的“data/trajectory.csv”，如果出发点变了，就可能是在找另一份文件。

日志像沿路留下的路标，摘要像实验结果旁的说明卡。它们的价值常在你忘了细节之后出现；所以第一次先把“输入在哪里、算了什么、输出在哪里”写清楚，已经很有用。

复盘时写一个具体场景：两周后我只拿到这张图，能否定位生成它的数据和命令？缺哪一项就补哪一项，不需要先做复杂实验平台。
